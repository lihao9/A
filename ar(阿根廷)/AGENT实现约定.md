# AGENT 一次性实现约定（AR 全模块共用）

> 本目录 **01 及之后每一份模块文档** 都按本文执行；实现 agent 一次性落地时也只认本文 + 该模块正文 + [`00-基础信息清单.md`](./00-基础信息清单.md)。  
> UI 空表扫描流程见 [`UI链接扫描规则.md`](./UI链接扫描规则.md)。  
> 全局防关联见 [`../独立开发者账号-新App防关联工程清单.md`](../独立开发者账号-新App防关联工程清单.md)。  
> 模块索引：[`modules-index.md`](./modules-index.md)。

梳理新模块、改旧模块、写代码前都先读本文。**模块正文只写该模块业务；通用门禁不在各篇重复发明。**  
**本目录文档是通用实现说明书**：换实现仓库、不打开任何对照源码，也应能按正文落地。  
**手段跟壳：** 导航、网络、存储、相机取流、进程入口用**当前工程已有实现**。模块正文只写职责。禁止把 Compose / 单 Activity / 某网络库 / CameraX 写成唯一实现。空仓库且未指定端：停问使用者（原生 Android / Flutter / 其它），不要从本文推断必须某一套 UI 框架。

## 1. 唯一依据

1. 实现时只依据：本约定 + `00` + **正在实现的那篇模块文档**。  
2. 缺信息标 TBD 或问使用者，**不要**去翻外部仓库补逻辑、补文案、补色值。  
3. 梳理阶段用来对照功能的工程或 UI，只证明「业务有没有覆盖」，**不是**实现稿，不得把对照工程的字符串、色值、类名写进实现代码。  
4. **模块 md 禁止对照指纹**：不得写入对照工程的类名、方法名、包路径、SP/常量字符串、混淆片段、密钥、以及「禁止与某某同名」清单。防关联要求用本条约定 §3（职责名 + 本包风格）一笔带过即可。代码层快评分只出现在对话，不写入模块文档。

## 2. 接口与字段

> **正文管 `o_`，代码管 wire；禁止把 `o_` 写进 JSON。**  
> 模块正文只写语义名；序列化字段名必须来自本包 API 文档的 wire（或明文协议字面量）。细则见 §2.3。

1. 路径写作 `ori: /xxx/yyy`。实现时从 `00` §6 指定的本包 API 文档查真实 path。  
2. 模块正文只写 `o_xxx`，禁止对照工程混淆字段。真实 wire 从 `00` §6 本包 API 映射。  
3. **`o_xxx` 是语义名，不是 JSON key（硬规则）：**  
   - 请求/响应 body、Header 的序列化字段名 = 本包 API 文档中的 **wire**（混淆名），或文档写明的**明文协议字面量**（如 `password`、`type`、`data`、`model`）。  
   - **禁止**把 `o_userId`、`o_smsItems` 等写进 `@SerializedName` / `json key` / 等价注解当线上字段名。  
   - **禁止**用「TODO 待确认 wire」「先用 o_ 占位」等方式入库；API 已有映射必须用；查不到 → 标 TBD **停问**，不得编。  
   - 「某采集项未交付 / 可空 / 本波不做」只约束**采不采、送不送**，**不表示** wire 名未知；API 条目里已有 wire 仍按 wire 写模型。  
   - 风控等特殊结构（如整包上报体、`req_body_other`、具名 VO）必须打开**对应接口条目**核对字段表，不得用模块语义名拼一套「看起来像业务」的 key。  
4. `data`、`title`、`content` 等协议原字面量不强行补不存在的 `o_xxx`。  
5. API 文档有、但该模块客户端未声明或未读取的字段，不得自行加入该模块判断。  
6. 未指定本包 API 前：可搭 UI/状态机，禁止臆造 wire 名入库。  
7. **落代码时的注释（跟本包 API 文档元数据，有则写、无则跳过，禁止自编）：**  
   - 接口 / 请求方法 / Remote 入口：API 条目有 **`title`** → 用作该接口的注释（接口名称）。  
   - 请求/响应字段（含 Header、body 属性）：API 字段有 **`desc`** → 用作该字段的注释（字段说明）。  
   - 文档没有 `title` / `desc`（或缺该键）→ **不写**对应注释，也不要用模块正文或对照工程文案顶上。

## 3. 符号与分层

类名、路由名、文件名、组件层次按**当前工程已有风格**设计；没有壳时按本包自定，且模块文档只使用**职责名**。禁止照搬对照工程的包路径、类结构、调用栈形状。

实现手段优先级：

1. 当前工程已有壳（网络出门、导航、槽读写、进程冷启、相机预览）；  
2. 该模块正文里的「某端附录」（仅当工程就是该端且壳尚未覆盖）；  
3. 空仓库：停问选端，禁止在业务模块里新发明一套与壳平行的公共层。

本地持久化：只认 [`00-基础信息清单.md`](./00-基础信息清单.md) §8 的**职责槽**。同一槽全工程一套读写；后做的模块禁止再声明平行存储。真实 key 字符串实现时自定一次即可。新槽先改 `00` §8 再写代码。加密与否、DataStore 还是系统偏好，跟壳。

## 4. 梳理阶段 vs 实现阶段

| 阶段 | 做什么 | UI 链接表 |
|------|--------|-----------|
| 梳理模块文档 | 写清业务判定、接口、测试矩阵；对照稿只核功能是否齐 | **保持空**（状态=未提供） |
| 一次性实现 | 向使用者要**本包实现用** Figma 项目链接 → 扫描 → 确认 → 填表 → 对稿写 UI | 填确认后的画板 |

对照用过的 UI 链接 **不算** 已提供实现稿。实现 agent 看到空表，必须按扫描规则重新要链接、重新确认。

## 5. 业务写死，外观当变量

| 类型 | 例子 | 写在哪 | 换 UI 链接时 |
|------|------|--------|----------------|
| 业务 | 状态码含义、显隐条件、点击去向、字段取值、门禁顺序 | 模块正文 | **不改** |
| 外观 | 颜色、字重、描边/实底、间距、圆角、切图 | 该模块「视觉变量表」 | 只改该表「最终样式」 |
| 文案 | 按钮字、标题、占位、错误提示 | 该模块「元素对照表」最终文案列 | 只改该列 |

正文可以写「状态 2 = 逾期未结清，用变量 `X-STYLE-PERIOD-OVERDUE`」，**禁止**写死「必须红色」。实现时从确认画板取样填进视觉变量表，再写进代码。

稿面没有对应态：业务判定仍按正文；外观/文案标「稿面未覆盖」并问使用者，**禁止**用对照工程的色值或字符串顶上。

## 6. 元素按功能编号，不按文案找

1. 每个可点或需对稿的界面元素给稳定编号：`{模块前缀}-{角色}-{职责}`。  
   - 前缀示例：启动 `S`、登录 `A`、首页 `H`、授信 `C`（后续模块自定时在该篇 §0 声明，全模块不重复）。  
   - 角色示例：`BTN` / `ENTRY` / `LINK` / `OPT` / `INPUT` / `CARD` / `STYLE`。  
2. 正文引用编号 + 功能（点了去哪、绑哪个字段）。  
3. 画板名、图层路径、node-id、可见文案集中在该模块元素对照表；换稿只改表，**正文不写死界面文案**。  
4. **按功能和位置找元素**。不得用某版稿上的按钮字当查找锚点。  
5. 找不到编号对应元素，或出现正文没有的新入口：停下来问使用者，不自行增删功能。

---

## 7. 文案

1. 界面可见文案以**确认后的实现用画板**为准，回填该模块元素对照表「最终文案」列。  
2. **模块正文不写死**具体按钮字、标题、说明句（含西语/中文 UI 句）；文档阶段元素表「当前稿文案」列也留空，对位后再填「最终文案」。  
3. 不得自行翻译，不得沿用对照工程 `strings.xml`。  
4. 「主按钮」= 页面上引导用户往下走的主要行动按钮（英文资料常写作 CTA）。各模块正文用「主按钮」，不要只写 CTA。

---

## 8. 组件集 ≠ 页面上有

判断「这一页有没有某入口」只看**已确认页面 Frame 的实例图层树**，不看文件级 `COMPONENTS` 清单，不看组件集里还有哪些变体。库里有图标 ≠ 本页有入口。不要让设计为了少误判去删组件库变体。细节见扫描规则 §3.1。

职责名也不要和画板标题强行对译。画板叫「虚拟首页」「首页-默认」时，以模块术语表为准，扫描用「匹配关键词」列，写代码用职责名。

---

## 9. 每个模块「UI 设计交付」必须有的三张表

编号可随篇章调整（01 用 §12、02/03 用 §14），**结构必须齐**：

| 表 | 作用 |
|----|------|
| 链接登记表 | 职责页 ↔ 画板关键词 / 确认后的链接 |
| 元素对照表 | 元素编号 ↔ 功能定位 ↔（可选）当前稿文案 ↔ node-id ↔ **最终文案**；文档阶段文案列留空 |
| 视觉变量表 | 样式编号 ↔ 绑定的业务态 ↔ 在画板上取什么 ↔ **最终样式** |

实现 agent 顺序：扫描画板 → 使用者确认登记表 → 按功能填元素表 → 从同一套画板取样填视觉变量表 → 才写界面与切图。

默认布局（顶栏固定、内容可滑、底栏吸底等）只在无稿或稿未规定时使用；有确认稿则以稿为准。用该端现有页面脚手架实现，不要求 Compose 或单 Activity。

切图：确认链接后可从稿导出则按稿密度（常见 3x）；禁止手画或 AI 仿图标。资源目录跟本工程（Android 原生未另定时可用 `mipmap-xxhdpi` 作建议）。占位规则见工程切图约定。

### 9.1 对稿自适应（优先 padding / margin）

画板上的 Frame 宽高是**当前文案下的快照**，不是必须写进代码的固定尺寸。

1. 默认跟内容走：从稿取样并写死的是 **padding、margin、gap、圆角、描边粗细、字号字重**。  
2. 不要把某一图层的 width / height 抄成唯一宽高。  
3. 成组横排/竖排用间距排开；只有稿明确要求拉满父级、最大宽度或固定图标槽时才锁尺寸（如顶栏高度、主按钮高度）。  
4. 视觉变量表记间距与色/圆角，不要把单卡 width 填成最终样式。  
5. **文案行数**：稿面或产品**没有**明确要求「单行 / 超出省略」时，**不要**给 Text 默认加 `maxLines = 1`（或等价单行截断），避免被布局压窄后莫名裁切。  
6. **横排（文案 + 按钮）**：谁吃剩余宽度要按稿意图，不要为了「一行对齐」顺手给文案加单行截断。常见注意：  
   - 按钮吃剩余（如 Compose `Modifier.weight(1f)`）、文案 wrap 内容：文案通常更不易被截；  
   - 文案吃剩余并配单行截断：接受省略时才这样写；  
   - 两边都抢剩余、或文案被压窄后再加单行：最容易展示不全。

## 10. 不一致先确认

梳理或实现对上对照功能、对照稿、本包稿三方时：

- 功能有无、状态机、接口：以模块正文（及已确认的业务口径）为准；对不上先问使用者，禁止猜。  
- 文案、颜色、有无某入口：以确认后的实现用画板为准；画板与正文冲突，先列差异再改文档，禁止静默改业务。

## 11. 梳理新模块时（写文档的 agent）

1. 先写业务：范围、判定、接口、测试矩阵。  
2. 对照外部功能只核「有没有漏态」，不把对照工程的色值/文案/类名/方法名抄进正文；落笔只留业务意图与本包协议。  
3. 外观一律预留元素编号 + 视觉变量，表留空。  
4. 通用门禁（本约定已有的）不要在新篇再写一套互相矛盾的说法；只写本模块增量。  
5. 术语与已有模块冲突时（例如「默认首页」），在该篇术语表写清，并在登记表用不同的匹配关键词。  
6. 收尾自检：换一套 UI 链接时，是否只需改三张表、不必改状态码段落。  
7. 不写网络库、架构、导航框架、UI 框架选型。跨模块只写职责跳转与门禁，壳专篇允许没有。  
8. 收尾再扫一遍：实现者是否必须打开外部源码才能看懂某句；若是，改成职责表述或删掉。  
9. 正文不把某端 API（如 `Application.onCreate`、CameraX、Manifest）写成各端唯一实现；需要时用「本端附录」或「跟壳」。

---

## 12. 实现时（写代码的 agent）

1. 读本约定 + `00` + 该模块。  
2. UI 表空则走扫描规则，确认前不写布局。  
3. **先跟当前工程壳**，再写本模块页面与接口；禁止平行再搭一套网络/存储/导航。  
4. 业务代码只依赖正文状态码/字段；strings 与颜色只依赖元素表「最终文案」和视觉变量表「最终样式」。  
5. 布局按 §9.1：能 hug + padding/margin 就不要写死画板宽高；Text 无单行要求不默认 `maxLines = 1`；横排文案+按钮注意谁 weight / 谁 wrap。  
6. 仿关联：实现后按工程要求做代码层快评（模式 B）。  
7. **字段/规则表对勾（防「完整版」漏细项）：**  
   - 模块正文若有字段全表、采集规则表、测试要点表（如 [`风控上报共用.md`](./风控上报共用.md) §2 / §4），收尾前必须**逐行对照代码**：有实现 / 文档允许空或失败兜底 / **未做**。  
   - 存在「未做」时：**禁止**在提交说明或对使用者回复里写「完整版 / 已做完 / 齐了」；须列出未做项，或当场补完后再收尾。  
   - 允许的空：**仅**文档写明的（词表空→数组空、读失败→`-1`/空串/省略 key）。**禁止**用空数组/空对象给「文档要求采集、尚未编码」的槽位打桩后称为完成。  
   - 大波次（上报+OCR 等）同一会话交付时，仍按上条对**本波涉及的每张字段表**做对勾；来不及做的细项写进对话未做清单，不得静默占位。

---

## 13. 整包怎么「一次性」落地

不要在一次对话里实现整个 App。业务文档按模块先写完（壳专篇不作为前置）。写代码按 [`整包落地顺序.md`](./整包落地顺序.md) 分波次；框架由实现者自定。未定稿模块只留路由占位。
